PHP FUNDAMENTALS – NOTES (UP TO MIXED ARRAYS)
Date: 01/08/2026
----------------------------------------------------------------

1. WHAT PHP IS
- Server-side scripting language.
- PHP code runs on the server; the browser receives only output.
- Loosely typed: data types assigned automatically.
----------------------------------------------------------------

2. RUNNING PHP

2.1 CLI (Command Line Interface)
- Used mainly for learning and scripting.
- Command: php filename.php
- Recommended for learning.
- New line character: \n
- HTML tags (e.g., <br>) are printed as plain text.
- Output shown in the terminal.
----------------------------------------------------------------

2.2 Browser (Server Execution)
- PHP runs through a web server (e.g., Apache or PHP built-in server).
- Output rendered as HTML.
- Line break in browser: <br>
- Browser ignores \n.
----------------------------------------------------------------

3. BASIC PHP SYNTAX
- PHP code starts with <?php (closing tag ?> optional).
- Every PHP statement ends with a semicolon (;).
----------------------------------------------------------------

4. VARIABLES
- Start with $.
- Case-sensitive.
- Must start with a letter or underscore (_).
Examples:
- $name = "Pranav";
- $age = 22;
- $isDeveloper = true;
----------------------------------------------------------------

5. DATA TYPES
- Common types: string, integer, float, boolean, array.
Examples:
- $name = "Dexter"; // string
- $age = 22; // integer
- $height = 5.9; // float
- $isActive = true; // boolean
----------------------------------------------------------------

6. DEBUGGING VARIABLES

6.1 var_dump()
- Inspect variables in detail.
- Shows type and value.
- Intended for debugging.

6.2 print_r()
- Cleaner output for arrays.
- Less detailed than var_dump().
- Intended for debugging only.
----------------------------------------------------------------

7. OUTPUT METHODS

7.1 echo
- Outputs text. No return value.
- Example: echo "Hello";

7.2 print
- Outputs text. Returns 1.
- Example: print "Hello";
----------------------------------------------------------------

8. STRINGS
- Double quotes (""): variables interpolated, escapes work.
  Example: echo "Hello $name\n";
- Single quotes (''): variables literal, escapes limited (\\ and \').
  Example: echo 'Hello $name\n';
----------------------------------------------------------------

9. STRING CONCATENATION
- Use dot operator (.).
- Example: echo "Hello " . $name;
----------------------------------------------------------------

10. CLI VS BROWSER OUTPUT
- CLI: newline is \n.
- Browser: line break is <br>.
----------------------------------------------------------------

11. CONDITIONS

11.1 if / else
- Example:
  if ($age >= 18) {
    echo "Adult";
  } else {
    echo "Minor";
  }

11.2 elseif
- Example:
  if ($marks >= 90) {
    echo "Grade A";
  } elseif ($marks >= 60) {
    echo "Grade B";
  } else {
    echo "Fail";
  }
----------------------------------------------------------------

12. COMPARISON OPERATORS
- == equal
- != not equal
- > greater than
- < less than
- >= greater than or equal
- <= less than or equal
----------------------------------------------------------------

13. LOGICAL OPERATORS
- && AND
- || OR
- ! NOT
- Example:
  if ($age >= 18 && $isDeveloper) {
    echo "Adult developer";
  }
----------------------------------------------------------------

14. ARRAYS

14.1 Indexed arrays
- Example: $fruits = ["Apple", "Banana", "Orange"];
- Index starts at 0.

14.2 Associative arrays
- Example:
  $user = [
    "name" => "Dexter",
    "age" => 22
  ];
- Access: echo $user["name"];

14.3 Mixed / nested arrays
- Example:
  $profile = [
    "user" => ["name" => "Dexter", "age" => 22],
    "skills" => ["PHP", "Laravel", "Git"],
    "isActive" => true
  ];
- Access:
  echo $profile["user"]["name"];
  echo $profile["skills"][1];
----------------------------------------------------------------

15. DEBUGGING ARRAYS
- print_r($profile) — readable.
- var_dump($profile) — detailed.
----------------------------------------------------------------

16. GIT LEARNING WORKFLOW
- One concept = one commit.
- Commit messages should describe what was learned.
- Example: "Understand PHP strings and concatenation"

WHAT IS DYNAMIC INPUT
- Input that is not hardcoded; comes from outside the PHP file.
- Examples: command line args, user typing at terminal, URL parameters, HTML form input.
- Dynamic input is untrusted.

WHAT ARE SUPERGLOBALS
- Predefined arrays available anywhere in the script.
- Common superglobals:
  - $argv → command line input
  - $argc → number of CLI arguments
  - $_GET → URL parameters
  - $_POST → form data
  - $_SERVER → request and environment info
----------------------------------------------------------------

CLI INPUT USING $argv
- php file.php 5 → $argv[0] = "file.php", $argv[1] = "5"
- $argv exists ONLY in CLI.
- All values are strings.
- Real input starts from $argv[1].
- Example: $limit = (int) $argv[1];
- Validate: if (!isset($argv[1]) || !is_numeric($argv[1])) { exit; }
----------------------------------------------------------------

RUNTIME INPUT USING STDIN
- fgets(STDIN) reads one line; trim() removes newline.
- Example: $name = trim(fgets(STDIN));
- Used only in CLI.
----------------------------------------------------------------

BROWSER INPUT USING $_GET
- URL: file.php?name=Pranav&age=21 → $_GET["name"] = "Pranav"
- Safe access: $name = $_GET["name"] ?? "Guest";
- All $_GET values are strings.
----------------------------------------------------------------

BROWSER INPUT USING $_POST
- $_POST receives form data sent via POST.
- Safe access: $username = $_POST["username"] ?? "";
- Check request method before using.
----------------------------------------------------------------

$_SERVER AND REQUEST_METHOD
- $_SERVER contains metadata.
- Important key: $_SERVER["REQUEST_METHOD"] ("GET" or "POST").
- Example:
  if ($_SERVER["REQUEST_METHOD"] === "POST") {
    // handle form data
  }
----------------------------------------------------------------

PHP_SAPI (EXECUTION ENVIRONMENT)
- Tells how PHP is running:
  - "cli" → terminal
  - "cli-server" → PHP built-in server
  - "apache" → web server
- Example:
  if (PHP_SAPI === "cli") {
    // CLI-only code
  }
----------------------------------------------------------------

WHY INPUT VALIDATION IS REQUIRED
- Input can be missing, empty, wrong type, or malicious.
- Validation ensures:
  - Input exists
  - Input is usable
  - Program does not continue with bad data
- Fail early using exit.
----------------------------------------------------------------

isset() VS empty()
- isset(): checks if variable exists (false if missing or null).
- empty(): checks if value is meaningful (true for "", 0, "0", null, false, []).
- Combined usage:
  if (!isset($var) || empty($var)) { exit; }
----------------------------------------------------------------

TYPE VALIDATION
- Dynamic input arrives as STRING.
- Use is_numeric(), strlen(), (int) $value to validate types.
----------------------------------------------------------------

WHAT IS XSS (CROSS-SITE SCRIPTING)
- Occurs when user input contains HTML/JS and PHP outputs it directly.
- Browser executes injected code.
- Example attack: <script>alert("Hacked")</script>
----------------------------------------------------------------

XSS PROTECTION: htmlspecialchars()
- Use when displaying untrusted input:
  echo htmlspecialchars($username, ENT_QUOTES, "UTF-8");
- Converts < > " ' into safe text.
- Seeing script tags printed as text means protection worked.
----------------------------------------------------------------

IMPORTANT SECURITY RULE
- Do NOT sanitize input when storing.
- Escape only when displaying output.
- Flow: Input → Validate → Use → Escape on output.
----------------------------------------------------------------

SECURITY MENTAL MODEL
- Receive input
- Check existence
- Check validity
- Use safely
- Escape before output
----------------------------------------------------------------

SUMMARY
- GET: request data
- POST: send data
- Uploads: POST only
- Avoid refreshing after POST; use redirect (PRG pattern) to prevent duplicate actions
- Headers control response flow
----------------------------------------------------------------

SESSIONS
- Without sessions: each request is independent (data is lost on refresh)
- With sessions: data persists across requests via a server-side store and session ID
- Start a session with `session_start()` and store data in `$_SESSION`
----------------------------------------------------------------

SESSION FLASH MESSAGES
- Use to show data once and then remove it:
  - Set: `$_SESSION['error'] = 'Message';`
  - Read & clear: `$error = $_SESSION['error'] ?? ''; unset($_SESSION['error']);`
- `unset()` removes a variable or array key entirely (different from setting to null)
----------------------------------------------------------------

HTTP REQUEST FLOW — GET vs POST
- HTTP is stateless; each request is independent
- GET: parameters in URL, safe to refresh and bookmark
- POST: data in request body, not safe to refresh
----------------------------------------------------------------

PRG: POST → REDIRECT → GET
- Process POST, then `header('Location: page.php'); exit;` to initiate a new GET request
- Always send `header()` before any output and call `exit` after redirect
----------------------------------------------------------------

HEADERS IN PHP (quick rules)
- `header('Location: page.php')` — redirect
- `header('Content-Type: text/html')` — set content type
- Headers must be sent before any output
----------------------------------------------------------------

PASSWORD HASHING & AUTH
- Never store plaintext passwords
- Use `password_hash()` to create a secure hash and `password_verify()` to check it:
  - `$hash = password_hash($password, PASSWORD_DEFAULT);`
  - `if (password_verify($inputPassword, $hash)) { /* ok */ }`
- Do NOT use fast hashes (md5, sha1, sha256) for passwords
----------------------------------------------------------------

AUTH FLOW (LOGIN)
- User submits login form (POST)
- Verify username exists and password with `password_verify()`
- On success: set `$_SESSION['username'] = $username` and redirect to a GET page
- Logout: `session_destroy()`
----------------------------------------------------------------

PHP IN HTML (SERVER-SIDE RENDERING)
- PHP runs on the server; the browser receives generated HTML
- Use `<?= $variable ?>` as shorthand for `<?php echo $variable ?>`
- Alternative syntax (e.g., `<?php if (cond): ?>...<?php endif; ?>`) helps when mixing logic and templates
----------------------------------------------------------------

RUNNING PHP FILES
- CLI: `php filename.php` (no HTTP, no sessions by default)
- Built-in server: `php -S localhost:8000` and open `http://localhost:8000/file.php`
- Do NOT use Live Server for PHP
----------------------------------------------------------------

COMMON MISTAKES
- Forgetting to redirect after POST (no PRG)
- Missing `session_start()`
- Not validating or escaping inputs
- Refreshing POST responses (duplicate actions)
- Storing clear-text passwords
----------------------------------------------------------------

FINAL CORE TAKEAWAYS
- HTTP is stateless; use sessions for persistence
- Always redirect after POST to avoid duplicate actions
- Hash and verify passwords correctly (`password_hash` / `password_verify`)
- Validate inputs and escape output (`htmlspecialchars`) when rendering

17. PROTECTED ROUTES (ACCESS CONTROL)
- Protected route means: A page that should only be accessible to logged-in users.
- Implementation logic: Check authentication at the very top of the file.
- Do NOT render HTML before the check.
- Redirect unauthenticated users.
- Core check:
  if (!isset($_SESSION['username'])) {
    redirect to login
    exit
  }
- Important points:
  - Protection is server-side.
  - Links alone do not protect pages.
  - exit after redirect is mandatory.
  - This is manual middleware logic.
  - Frameworks later centralize this logic, but behavior is the same.
----------------------------------------------------------------

18. REGISTRATION / SIGNUP FLOW
- Registration means: Creating a new user securely.
- Hashing password before storage.
- In this phase: No database is used.
- User data is simulated using session storage.
- User storage: $_SESSION['users'] = [];
- Each user stored as: username => hashed_password
- Registration flow:
  - User submits signup form (POST).
  - Input is validated (not empty).
  - Check if username already exists.
  - Password is hashed using password_hash().
  - User is stored.
  - Success message is set in session.
  - Redirect happens.
  - GET request renders page.
----------------------------------------------------------------

19. SESSION AS STORAGE
- $_SESSION is just an array.
- Examples:
  - $_SESSION['users']
  - $_SESSION['username']
  - $_SESSION['error']
  - $_SESSION['success']
- These are NOT built-in.
- They are user-defined keys.
- PHP does not care about the key names.
- You choose the names and their meaning.
----------------------------------------------------------------

20. FLASH MESSAGES (ERROR / SUCCESS)
- Flash message = message shown once, then removed.
- Pattern:
  $_SESSION['error'] = "Error message";
  On next request:
  $error = $_SESSION['error'] ?? '';
  unset($_SESSION['error']);
- Purpose:
  - Show feedback once.
  - Prevent message repeating on refresh.
  - Same logic applies to success messages.
----------------------------------------------------------------

21. unset() FUNCTION
- unset() completely removes a variable or array key.
- Difference:
  - unset($x) → variable removed
  - $x = null → variable exists with null value
  - $x = '' → variable exists with empty string
- Used for:
  - Flash messages.
  - Temporary session data.
  - Cleaning up session state.
----------------------------------------------------------------

22. PASSWORD HASHING RULES
- Passwords must NEVER be stored in plain text.
- Correct functions:
  - password_hash()
  - password_verify()
- Hashing properties:
  - One-way.
  - Cannot be reversed.
  - Same password gives different hash each time.
  - Includes salt automatically.
- Do NOT use:
  - md5()
  - sha1()
  - sha256()
- Hashing is NOT encryption.
----------------------------------------------------------------

23. POST → REDIRECT → GET (PRG PATTERN)
- After any POST that changes state: Always redirect.
- Never stay on POST.
- Why:
  - Prevent duplicate actions.
  - Prevent form resubmission.
  - Make refresh safe.
- PHP implementation:
  header("Location: page.php");
  exit;
----------------------------------------------------------------

24. PHP INSIDE HTML (SERVER-SIDE RENDERING)
- PHP runs first on server.
- HTML is sent to browser after PHP finishes.
- Alternative PHP syntax:
  <?php if (condition): ?>
    HTML
  <?php endif; ?>
- Purpose:
  - Clean mixing of logic and HTML.
  - PHP decides which HTML exists.
  - Browser never sees PHP code.
----------------------------------------------------------------

25. SESSION KEY TAKEAWAYS
- $_SESSION is just an array.
- You define the keys.
- Session data survives refresh and redirect.
- Session represents authentication state.
- Flash messages are temporary session values.
