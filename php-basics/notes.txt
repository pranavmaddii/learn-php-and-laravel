PART 1: BASICS
================================================================================

1. WHAT PHP IS
- Server-side scripting language
- Loosely typed: data types assigned automatically
- Code runs on server; browser receives only output

2. RUNNING PHP

2.1 CLI (Command Line Interface)
- Command: php filename.php
- Newline character: \n
- HTML tags printed as plain text
- Output shown in terminal

2.2 Browser (Web Server)
- Runs through Apache or PHP built-in server
- Output rendered as HTML
- Line break: <br> (browser ignores \n)
- Built-in server: php -S localhost:8000

3. BASIC SYNTAX
- Code starts with <?php (closing tag ?> optional)
- Shorthand: <?= $variable ?>
- Every statement ends with semicolon (;)

4. VARIABLES
- Start with $
- Case-sensitive
- Must start with letter or underscore (_)

5. DATA TYPES
- string, integer, float, boolean, array

6. DEBUGGING
- var_dump() — detailed (type + value)
- print_r() — readable (arrays)

7. OUTPUT METHODS
- echo — no return value
- print — returns 1

================================================================================
PART 2: STRINGS & OPERATORS
================================================================================

8. STRINGS
- Double quotes (""): variables interpolated, escapes work
- Single quotes (''): variables literal, limited escapes (\\ and \')

9. STRING CONCATENATION
- Use dot operator (.)
- Example: echo "Hello " . $name;

10. COMPARISON OPERATORS
- ==, !=, >, <, >=, <=

11. LOGICAL OPERATORS
- && (AND), || (OR), ! (NOT)

================================================================================
PART 3: CONTROL FLOW
================================================================================

12. CONDITIONS
- if / else
- elseif
- Comparison and logical operators

13. ARRAYS

13.1 Indexed Arrays
- $fruits = ["Apple", "Banana", "Orange"];
- Index starts at 0

13.2 Associative Arrays
- $user = ["name" => "Dexter", "age" => 22];
- Access: $user["name"]

13.3 Mixed/Nested Arrays
- $profile = [
  "user" => ["name" => "Dexter", "age" => 22],
  "skills" => ["PHP", "Laravel", "Git"],
  "isActive" => true
  ];
- Access: $profile["user"]["name"], $profile["skills"][1]

================================================================================
PART 4: INPUT HANDLING & VALIDATION
================================================================================

14. DYNAMIC INPUT TYPES

14.1 CLI Input
- $argv (command line arguments)
- $argc (number of arguments)
- $argv[0] = filename, $argv[1] = first argument
- All values are strings
- Example: php file.php 5 → $argv[1] = "5"

14.2 Runtime CLI Input
- fgets(STDIN) reads one line
- trim() removes newline
- Example: $name = trim(fgets(STDIN));

14.3 Browser GET
- URL: file.php?name=Pranav&age=21
- Access: $_GET["name"]
- Safe access: $name = $_GET["name"] ?? "Guest";

14.4 Browser POST
- Form data sent via POST
- Access: $_POST["username"]
- Safe access: $username = $_POST["username"] ?? "";

15. SUPERGLOBALS
- $argv — CLI arguments
- $argc — CLI argument count
- $_GET — URL parameters
- $_POST — form data
- $_SERVER — request and environment info
  - KEY: $_SERVER["REQUEST_METHOD"] ("GET" or "POST")

16. PHP_SAPI (Execution Environment)
- "cli" → terminal
- "cli-server" → built-in server
- "apache" → web server

17. INPUT VALIDATION

17.1 isset() vs empty()
- isset() — checks existence (false if missing/null)
- empty() — checks meaning (true for "", 0, "0", null, false, [])
- Combined: if (!isset($var) || empty($var)) { exit; }

17.2 Type Validation
- Dynamic input arrives as STRING
- Use is_numeric(), strlen(), (int) $value
- Validate: if (!isset($argv[1]) || !is_numeric($argv[1])) { exit; }

17.3 Why Validation Required
- Input can be missing, empty, wrong type, or malicious
- Fail early using exit

18. SECURITY

18.1 XSS (Cross-Site Scripting)
- Occurs when user input contains HTML/JS and is output directly
- Browser executes injected code
- Example attack: <script>alert("Hacked")</script>

18.2 XSS Protection: htmlspecialchars()
- Use when displaying untrusted input
- echo htmlspecialchars($username, ENT_QUOTES, "UTF-8");
- Converts <, >, ", ' into safe text

18.3 Security Flow
- Receive input
- Check existence
- Check validity
- Use safely
- Escape before output
- DO NOT sanitize when storing; escape only on output

PART 5: HTTP & REQUEST HANDLING
================================================================================

19. HTTP REQUEST FLOW
- HTTP is stateless; each request is independent
- GET: parameters in URL, safe to refresh and bookmark
- POST: data in request body, not safe to refresh

20. POST → REDIRECT → GET (PRG PATTERN)
- Process POST, then redirect to new GET request
- Always prevent duplicate form submissions
- Implementation:
  header("Location: page.php");
  exit;
- Rules:
  - Send header() before any output
  - Always call exit after redirect

21. HEADERS IN PHP
- header('Location: page.php') — redirect
- header('Content-Type: text/html') — content type
- Must be sent before any output

PART 6: SESSIONS & AUTHENTICATION
================================================================================

22. SESSIONS BASICS
- Without sessions: each request is independent (data lost on refresh)
- With sessions: data persists across requests
- Start with: session_start()
- Store data in: $_SESSION array
- Sessions use cookies internally to store session ID

23. SESSION AS STORAGE
- $_SESSION is just a server-side array
- You define the keys (no built-in names)
- Key examples: $_SESSION['username'], $_SESSION['users'], $_SESSION['error']
- Data survives refresh and redirect

24. FLASH MESSAGES (Error/Success)
- Message shown once, then removed
- Set: $_SESSION['error'] = 'Message';
- Read & clear:
  $error = $_SESSION['error'] ?? '';
  unset($_SESSION['error']);
- Must use $_SESSION (not $_SERVER) to survive redirects

24.1 Why $_SERVER Does Not Work
- $_SERVER exists only for current request
- Does not persist across redirects
- Only for request metadata

25. unset() FUNCTION
- Completely removes variable or array key
- Differences:
  - unset($x) → variable removed
  - $x = null → variable exists, null value
  - $x = '' → variable exists, empty string

26. PASSWORD HASHING & AUTH

26.1 Password Rules
- NEVER store plaintext passwords
- Correct functions: password_hash(), password_verify()
- DO NOT use: md5(), sha1(), sha256()

26.2 Hashing Implementation
- Hash on storage: $hash = password_hash($password, PASSWORD_DEFAULT);
- Verify on login: if (password_verify($inputPassword, $hash)) { /* ok */ }
- Properties:
  - One-way (cannot be reversed)
  - Same password gives different hash each time
  - Includes salt automatically

26.3 Session Regeneration (Security)
- session_regenerate_id(true) after login
- Prevents session fixation attacks
- Frameworks do this automatically

27. AUTHENTICATION FLOW (LOGIN)

Step 1: User submits login form (POST)
Step 2: Verify username exists
Step 3: Use password_verify() to check password
Step 4: On success: set $_SESSION['username'] = $username
Step 5: Redirect to GET page
Step 6: Session persists across requests

Core session flag:
- If $_SESSION['username'] exists → user logged in
- If $_SESSION['username'] missing → user logged out

28. LOGOUT
- session_destroy() deletes all session data on server
- Session ID becomes useless
- User is logged out

29. REGISTRATION/SIGNUP FLOW

Step 1: User submits signup form (POST)
Step 2: Validate input (not empty)
Step 3: Check if username already exists
Step 4: Hash password: password_hash()
Step 5: Store user: $_SESSION['users'][username] = hashed_password
Step 6: Set success message in session
Step 7: Redirect (GET request)
Step 8: Render page with message

30. PROTECTED ROUTES (ACCESS CONTROL)
- Protected route: only accessible to logged-in users
- Implementation: Check auth at top of file
- DO NOT render HTML before check
- Code:
  session_start();
  if (!isset($_SESSION['username'])) {
  header('Location: login.php');
  exit;
  }
- Key points:
  - Protection is server-side
  - Links alone do NOT protect pages
  - exit after redirect is mandatory

PART 7: SERVER-SIDE RENDERING & FUNCTIONS
================================================================================

31. PHP IN HTML (SERVER-SIDE RENDERING)
- PHP runs on server first
- HTML sent to browser after PHP finishes
- Browser never sees PHP code

31.1 Alternative PHP Syntax
- <?php if (condition): ?>
  HTML
  <?php endif; ?>
- Cleaner mixing of logic and HTML
- PHP decides which HTML exists

32. FUNCTION-BASED DESIGN (CONCEPTUAL)

Purpose:
- Avoid repetition
- Centralize logic
- Improve readability
- Prepare for frameworks

Example auth helpers:
- isLoggedIn() — returns true if logged in
- login() — regenerates session, stores username
- logout() — destroys session, redirects
- flashMsg() — reads session value once, deletes it
- redirect() — centralized redirect logic

34. COMMON MISTAKES

- Storing plaintext passwords

================================================================================
CORE MENTAL MODELS
================================================================================

HTTP Statefulness:
- HTTP is stateless; each request is independent
- Use sessions for persistence across requests

Request Types:
- GET: Read/render pages, safe to refresh/bookmark
- POST: Submit data, must redirect, not safe to refresh

Session Mechanics:
- $_SESSION is server-side array
- Browser stores only session ID (cookie)
- Data survives refresh and redirect
- Only sessions survive redirects (not $_SERVER)

Authentication State:
- Determined by presence of $_SESSION['username']
- Set on login, cleared on logout
- Checked at top of protected routes

Input Security:
- Validate on input (existence, type, format)
- Escape on output (htmlspecialchars)
- Never sanitize when storing
- Always hash passwords before storage

Flash Messages:
- Use for POST feedback
- Stored in $_SESSION
- Read once then unset()
- Survive redirect once, then disappear
